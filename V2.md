# MelonisWiki API v2

API v2 позволяет интеграциям читать и изменять статьи, получать историю версий и работать с общей очередью модерации. Доступ выдаёт администрация в виде API-ключа, привязанного к пользователю вики.

Базовый URL: `https://melonis.wiki/api/v2`.

API v1 остаётся по адресу `GET /api/fetch` с прежними форматами ответов, но требует собственный ключ v1, который пользователь запрашивает в профиле ([подробнее](README.md#ключ-api)). Ключ v2 не работает в v1 и наоборот (`403 WRONG_API_VERSION`). История статей на сайте также остаётся публичной. Ограничения ключа ограничивают v2, а не доступность опубликованного содержимого через сайт или v1.

## Получение и хранение ключа

Администратор выбирает владельца, действия, область доступа, правила публикации, лимиты и срок действия. По умолчанию новый ключ не имеет разрешений, требует проверки публикаций и истекает через 90 дней. Администратор может явно разрешить бессрочную работу.

Секрет имеет формат `mwk_…`. Администратор видит его только при создании или замене и передаёт владельцу отдельно. В базе хранится только SHA-256 хеш; повторно получить секрет невозможно. При замене старый секрет сразу перестаёт действовать.

Передавайте ключ только через заголовок:

```bash
curl 'https://melonis.wiki/api/v2/me' \
  -H "Authorization: Bearer $MELONIS_API_KEY"
```

Cookie, другие токены доступа и параметры URL не заменяют ключ. Все методы под `/api/v2`, включая `OPTIONS`, требуют ключ. API рассчитан на серверные интеграции; браузерный cross-origin доступ не включён. Храните секрет на сервере, исключайте его из журналов и исходного кода.

Заблокированный владелец, отключённый, истёкший или отозванный ключ получает `401`. После разблокировки владельца или включения ключа он снова действует, если остальные условия выполнены. Отзыв необратим; он сохраняет отправки, версии и их авторство. Замена секрета не продлевает срок действия и сохраняет идентификатор ключа.

## Разрешения и область доступа

| Разрешение | Действия |
|---|---|
| `articles:read` | Разделы, список/поиск статей, чтение статьи |
| `articles:create` | Создание статьи |
| `articles:edit` | Редактирование существующей статьи |
| `history:read` | История и полные снимки версий |
| `queue:read` | Список и содержимое ожидающих проверки отправок |
| `queue:approve` | Одобрение отправки по ID |
| `queue:reject` | Отклонение отправки по ID |

Права независимы. Например, `history:read` не выдаёт `articles:read`, а `queue:approve` не выдаёт `queue:read`. Статус участника вики не расширяет и не ограничивает права ключа.

Действует одна область доступа для всех операций:

- `all`: все разделы и статьи;
- `sections`: только выбранные разделы;
- `articles`: только выбранные существующие статьи; создание новых запрещено.

При переносе статьи ключ должен иметь доступ к текущему и целевому разделам. Для очереди учитываются предложенный, исходный и текущий разделы. История возвращает только версии из разрешённых разделов и доступна только для статьи, к которой ключ имеет текущий доступ. Списки, поиск, разделы и счётчики пагинации фильтруются по этим правилам.

`GET /me` и просмотр собственной отправки не требуют отдельного разрешения. Проверка области доступа применяется и к собственной отправке.

## Общие форматы

Успешные ответы содержат `ok: true`. Ошибки:

```json
{ "ok": false, "code": "FORBIDDEN", "error": "Missing permission: articles:edit" }
```

Все ответы v2 содержат `Cache-Control: private, no-store`. Не используйте общие кэши для содержимого очереди и сведений о ключах. Инфраструктурный сбой до приложения может вернуть другой формат.

Списки принимают `page` (по умолчанию 1) и `limit` (по умолчанию 25, максимум 100). Больший корректный `limit` уменьшается до 100. Смещение `(page − 1) × limit` не может превышать 10 000 — для глубоких выборок сужайте запрос через `section` или `q`. Некорректные числа и слишком далёкие страницы возвращают `400 INVALID_PAGE`. Поиск `q` ищет подстроку буквально: `%` и `_` не работают как шаблоны. Ответ:

```json
{ "ok": true, "articles": [], "pagination": { "page": 1, "limit": 25, "total": 0 } }
```

Страницы за пределами результата пустые. Время возвращается в ISO 8601 UTC. ID и версии — положительные целые числа.

## Сведения о ключе

`GET /me` → `{ "ok": true, "key": { ... } }`.

DTO ключа содержит `id`, `ownerId`, `ownerUsername`, `name`, `description`, `prefix`, `permissions`, `boundaryType`, `sectionIds`, `articleIds`, `createPolicy`, `editPolicy`, `readLimit`, `mutationLimit`, `enabled`, `expiresAt`, `revokedAt`, `lastUsedAt`, `createdAt`, `requestCount`, `status`.

Поля времени могут быть `null`, если событие не происходило или срок не задан. Статусы: `active`, `disabled`, `expired`, `revoked`, `owner_banned`. Секрет и его хеш в DTO отсутствуют. Счётчики в `/me` отражают состояние перед учётом текущего запроса.

## Чтение статей

| Метод и путь | Результат |
|---|---|
| `GET /sections` | `sections`: `{ id, slug, name }[]` |
| `GET /articles` | `articles` и `pagination` |
| `GET /articles/{id}` | `article` |
| `GET /articles/{id}/history` | `history` и `pagination` |

Список статей принимает `section` — slug раздела, и `q` — строку до 200 символов для поиска по названию/содержимому. Результаты сортируются по времени обновления, затем ID, от новых к старым. Старые slug разделов разрешаются как на сайте. Поиск v2 использует сопоставление SQL LIKE; `%` и `_` имеют значение шаблонов SQL.

Статья:

```json
{
  "id": 42,
  "sectionId": 3,
  "sectionSlug": "projects",
  "slug": "example",
  "title": "Пример",
  "content": "Markdown статьи",
  "listIcon": null,
  "version": 2,
  "author": { "id": 7, "username": "Author" },
  "createdAt": "2026-10-18T10:00:00.000Z",
  "updatedAt": "2026-10-18T11:00:00.000Z"
}
```

История сортируется по убыванию версии. Элемент содержит `id`, `articleId`, `version`, `sectionId`, `sectionSlug`, `slug`, `title`, `content`, `listIcon`, `author: { id, username, type }`, `apiKey: { id, name } | null`, `changeSummary`, `createdAt`. Старые или административные записи могут не иметь автора-пользователя. Название ключа фиксируется при отправке, поэтому переименование не меняет авторство старых версий.

## Создание и изменение

- `POST /articles` — создать статью.
- `PUT /articles/{id}` — отправить полную замену редактируемого содержимого статьи.

Оба запроса требуют `Content-Type: application/json` (иначе `415 UNSUPPORTED_MEDIA_TYPE`) и UUID в заголовке `Idempotency-Key`. Это относится и к телам запросов модерации.

```bash
curl 'https://melonis.wiki/api/v2/articles' \
  -H "Authorization: Bearer $MELONIS_API_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 56286d9b-25d9-4cab-98da-590aa338d523' \
  --data '{"sectionSlug":"projects","title":"Пример","content":"Текст статьи","publicationMode":"review"}'
```

| Поле | Правило |
|---|---|
| `title` | Обязательно; после удаления внешних пробелов 1–200 символов |
| `content` | Обязательно; непустой Markdown, максимум 500 000 символов |
| `sectionSlug` | Обязательно при создании; при изменении по умолчанию текущий раздел |
| `baseVersion` | Обязательно при изменении; версия, на основе которой клиент подготовил правку |
| `listIcon` | Путь к существующему изображению `/uploads/{uuid}.{ext}`, либо `null`; пропуск удаляет иконку |
| `changeSummary` | Необязательная причина, максимум 255 символов; допускает `null` |
| `publicationMode` | `review` или `direct`; по умолчанию политика ключа для создания/изменения |

Неизвестные поля отклоняются. Тело ограничено 3 MiB в UTF-8. Slug генерируется из названия с существующей обработкой коллизий. Ссылки вики сохраняются через общий механизм сайта. API загрузки изображений не входит в v2; можно ссылаться на существующие изображения.

Для создания и изменения администратор задаёт отдельные политики. При `review` прямой режим возвращает `403 APPROVAL_REQUIRED`. При `direct` клиент может выбрать `review`.

Ответ при публикации — `201`, при постановке в очередь — `202`:

```json
{ "ok": true, "pendingId": 123, "articleId": null, "status": "pending", "published": false }
```

Опубликованный ответ содержит ID статьи, `status: "approved"` и `published: true`. Даже прямая публикация сохраняет запись отправки и версию. Вставка, история, решение и запись идемпотентности коммитятся атомарно.

Повтор идентичного запроса с тем же ключом и `Idempotency-Key` возвращает `200` и актуальный статус той же отправки. Идентификатор идемпотентности привязан к ID API-ключа, методу, статье и нормализованному JSON запроса; замена секрета не сбрасывает его. Другая операция или данные с тем же UUID возвращают `409 IDEMPOTENCY_MISMATCH`. Для новой отправки используйте новый UUID. Если администратор удалил исходную статью/отправку, повтор получает `410 SUBMISSION_REMOVED`: UUID сохраняется как отметка удаления, чтобы повтор не восстановил статью. Доступ и текущие ограничения повторно проверяются.

При несовпадении `baseVersion` запрос получает `409 VERSION_CONFLICT`. Получите новую версию статьи, объедините изменения и отправьте новую правку с новым UUID. Конфликт возможен и при одобрении ранее поставленной в очередь правки: одобрение не перезаписывает более новую версию.

## Собственные отправки

`GET /submissions/{id}` возвращает `{ "ok": true, "submission": { ... } }` только для отправки, созданной тем же ID ключа. Другой ключ того же владельца не получает доступ автоматически. Это работает без `queue:read`, в том числе после одобрения или отклонения.

Запись содержит `id`, `articleId`, `sectionId`, `sectionSlug`, `slug`, `title`, `content`, `listIcon`, `author: { id, username }`, `apiKey: { id, name } | null`, `originalTitle`, `originalContent`, `originalListIcon`, `originalSectionId`, `baseVersion`, `changeSummary`, `status`, `reviewNotes`, `createdAt`, `reviewedAt`, `reviewer: { type, userId, apiKeyId } | null`.

Статусы: `pending`, `approved`, `rejected`. У новых статей `articleId` становится известен после одобрения. У старых отправок некоторые поля исходного снимка и проверяющего могут быть `null`. Ключ с ограничением по разделам не получает старую конфликтующую отправку, если её исходный раздел нельзя подтвердить; администратор или ключ с полным доступом может проверить её.

## Модерация

| Метод и путь | Разрешение | Результат |
|---|---|---|
| `GET /moderation` | `queue:read` | `pending` и `pagination`, старые отправки первыми |
| `GET /moderation/{id}` | `queue:read` | `submission` со статусом `pending` |
| `POST /moderation/{id}/approve` | `queue:approve` | Публикация и новая версия |
| `POST /moderation/{id}/reject` | `queue:reject` | Отклонение без публикации |

Это общая очередь: доступны отправки как с сайта, так и через API. Элементы имеют тот же DTO, что собственные отправки.

Решения принимают JSON `{}` или `{ "notes": "Причина решения" }`. `notes` необязательно, допускает `null`, максимум 2000 символов. Успешный ответ — `200`, например `{ "ok": true, "status": "approved", "articleId": 42 }`. Повторное решение получает `409 NOT_PENDING`; оно не создаёт дополнительной версии. Одобрение конфликтующей версии получает `409 VERSION_CONFLICT`.

Владелец отправки не может одобрить её через свои API-ключи. API-отправку также нельзя одобрить через contributor-сессию того же пользователя на сайте. Одобрить может другой пользователь с нужными правами или администратор. Отклонение собственной отправки допускается при наличии `queue:reject`. Прямая публикация по явному разрешению ключа не считается обходом этого правила.

## Лимиты и ошибки

Лимиты общие для всех экземпляров сервера и хранятся в MySQL. Используются фиксированные окна UTC: минута для чтения и 10 минут для изменений. Значения по умолчанию — 300 и 25 запросов соответственно; администрация может менять их отдельно для каждого ключа.

Учитываются запросы с действительным ключом, допущенные лимитером, включая последующие ошибки валидации или разрешений. Отклонённые лимитером запросы не увеличивают счётчик. `lastUsedAt` и `requestCount` показывают такие допущенные запросы. Отдельная статистика ключа (сутки UTC × эндпоинт × класс статуса) учитывает все запросы, которые удалось связать с ключом, включая `429` и запросы отключённым ключом. Два бюджета независимы.

После 60 запросов с неверным или неактивным ключом за 10 минут с одного адреса сервер отвечает `429 AUTH_THROTTLED`, не проверяя ключ. При изменении настроек использованный бюджет текущего окна сохраняется.

При `429 RATE_LIMITED` соблюдайте `Retry-After` в секундах. Для временных `503` используйте ограниченное число повторов с backoff. При повторе отправки сохраняйте UUID идемпотентности и тело запроса.

| Статус | Коды / значение |
|---|---|
| `400` | `INVALID_INPUT`, `INVALID_ID`, `INVALID_PAGE`, `INVALID_QUERY`, `INVALID_JSON`, `INVALID_ICON`, `INVALID_IDEMPOTENCY_KEY` |
| `401` | `INVALID_KEY`, `INACTIVE_KEY` |
| `403` | `FORBIDDEN`, `OUTSIDE_BOUNDARY`, `APPROVAL_REQUIRED`, `SELF_APPROVAL`, `WRONG_API_VERSION` |
| `404` | `NOT_FOUND`; отсутствующая или недоступная для чтения запись |
| `405` | `METHOD_NOT_ALLOWED` |
| `409` | `VERSION_CONFLICT`, `IDEMPOTENCY_MISMATCH`, `NOT_PENDING`, `MISSING_UPLOAD` |
| `410` | `SUBMISSION_REMOVED` |
| `413` | `BODY_TOO_LARGE` |
| `415` | `UNSUPPORTED_MEDIA_TYPE` |
| `429` | `RATE_LIMITED`, `AUTH_THROTTLED` с `Retry-After` |
| `503` | `UNAVAILABLE` |

## Раздел разработчика в профиле

Ссылка «Разработчикам» в `/profile` видна всем вошедшим пользователям. На `/profile/developer` можно запросить ключ v1, получить его после одобрения, посмотреть все собственные ключи (v1 и v2, включая неактивные) и статистику запросов по каждому за 30 дней. Неавторизованному пользователю предлагается вход.

Ключи v2 в профиле доступны только для чтения: видны права, ограничения, политики, срок, статус, префикс и использование. Ключи v1 владелец может сам заменить или отозвать. Секретов, хешей и административного журнала в профиле нет.

Сессионные маршруты `/api/profile/api-keys` находятся вне v2 и отклоняют запросы с заголовком `Authorization`. Изменения проходят проверку Origin и ограничены 20 действиями за 10 минут.

| Метод и путь | Назначение |
|---|---|
| `GET /api/profile/api-keys` | `{ ok, keys, requests }` текущего пользователя |
| `GET /api/profile/api-keys/{id}/usage` | Счётчики собственного ключа за 30 дней (без IP) |
| `POST /api/profile/api-keys/requests` | `{ name, purpose }` — заявка на ключ v1; одна активная заявка, не больше 3 ключей v1, 24 часа после отказа |
| `POST /api/profile/api-keys/requests/{id}/cancel` | Отменить заявку на рассмотрении |
| `POST /api/profile/api-keys/requests/{id}/claim` | Получить ключ по одобренной заявке: `{ ok, key, secret }`, `201`, один раз |
| `POST /api/profile/api-keys/{id}/rotate` · `/revoke` | Заменить секрет или отозвать собственный ключ v1 |

## Управление администрацией

Эти маршруты требуют admin-cookie, а изменения дополнительно проходят проверку Origin. API-ключ не даёт доступ к управлению ключами.

| Метод и путь | Назначение |
|---|---|
| `GET /api/admin/api-keys?q=…&page=1` | Поиск по названию, владельцу или префиксу; по 25 записей |
| `GET /api/admin/api-keys/options?q=…` | Разделы и до 50 статей по названию/ID для формы |
| `POST /api/admin/api-keys` | `{ ownerId, apiVersion?, config }` (`apiVersion` — `v2` по умолчанию; для `v1` разрешения и ограничения должны быть пустыми); возвращает `{ ok, key, secret }`, `201` |
| `GET /api/admin/api-keys/{id}/usage` | Счётчики за 30 дней по эндпоинтам и классам статусов, `lastUsedIp` |
| `GET /api/admin/api-keys/requests?status=pending` | Заявки на ключи v1 (`pending`, `approved`, `issued`, `rejected`, `cancelled`, `all`) |
| `POST /api/admin/api-keys/requests/{id}/approve` | `{ readLimit?, expiresDays?, notes? }` — одобрить; ключ создаётся, когда пользователь его получит |
| `POST /api/admin/api-keys/requests/{id}/reject` | `{ notes }` — отклонить с причиной |
| `PATCH /api/admin/api-keys/{id}` | Частичное изменение config; возвращает `{ ok, key }` |
| `POST /api/admin/api-keys/{id}/rotate` | Возвращает `{ ok, key, secret }`; старый секрет аннулируется |
| `POST /api/admin/api-keys/{id}/revoke` | Необратимый отзыв; возвращает `{ ok, key }` |
| `GET /api/admin/api-keys/{id}/audit?page=1` | Журнал по 25 записей |

`config` содержит `name` (1–100), `description` (до 500), `permissions`, `boundaryType`, `sectionIds`, `articleIds`, `createPolicy`, `editPolicy`, `readLimit`, `mutationLimit`, `enabled`, `expiresAt` (ISO 8601 с часовым поясом или `null`). Лимиты — целые от 1 до 1 000 000. Идентификаторы ограничений должны существовать. Владелец неизменяем. Отозванные ключи нельзя изменить или заменить их секрет; такие операции возвращают `409 REVOKED_KEY`.

Аудит хранит тип действующего лица (`admin`, `user`, `api_key`), ID пользователя/ключа при наличии, действие, ID отправки/статьи и время. Изменения конфигурации содержат настройки до/после. Записи отправок и решений не содержат текста статьи или секретов. Индивидуальное имя администратора недоступно, поскольку текущая административная авторизация общая.
